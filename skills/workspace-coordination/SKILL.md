# G8 与工作区协调员职责和协作规范

公子于 2026-11-20 确认。G8 统筹跨项目工作，拥有 Task Mailbox 全部现有和后续项目的最高业务读写与操作权限，可以向任何 Multica 工作区的现任协调员发送指令和任务。此默认授权跟随 G8 已认证账号。新增项目沿用同一规则，接入新工作区时登记当地协调员。

## 谁负责什么

自 2026-11-21 起，项目进度、负责人、阻塞、复审和验收结论统一在所属 **Multica 项目看板**查询，由获授权的责任人沿原 Issue 更新。运行事实查关联 Run，交付依据可引用 GitHub Issue、PR 或提交。收到旧看板条目时，按已有引用定位 Multica 原卡；映射不明由协调员核对，避免重复建卡。历史看板记录仅供追溯。

| 角色 | 决定与交付 |
|---|---|
| G8 | 明确目标、优先级、资源取舍和验收人。项目或工作区之间出现冲突时，选定方案，给受影响的协调员下达一致的指令，向公子汇报结果或需要公子决定的事项。 |
| 工作区协调员 | 按目标工作区和当前任职登记接单，在所属项目创建或关联原 Issue。选择执行者、安排复审，在任务授权范围内决定实施路线，处理可就地解决的阻塞，向 G8 交付带证据的结果。 |
| 项目负责人 | 负责本项目的路线、分工、集成和约定的业务验收。用决策 MCP 比较会影响交付的可行选项，给执行者明确指令。跨项目资源冲突、目标或交期需调整时，带推荐方案报工作区协调员。 |
| 执行者、复审者与验收人 | 执行者提交产物和复现证据，复审者核对约定范围，指定验收人记录业务结论。运行事实引用原生 Run，读确认由实际收件方出具。 |

按 `workspace → 当前协调员 → project → Issue/Run` 找人和定位任务。例：`cloud-work` 的现任协调员是 Mike，内建岗位键为 `mika`。其他工作区从自己的原生登记解析。发生同名、换任或绑定冲突时，先核实该工作区的实际任职，再派该件。跨工作区任务由 G8 选一个牵头协调员，其他协调员分别接有明确边界的子任务。

## 怎样快速判断

G8、各工作区协调员及已确认任职的项目负责人默认获准使用 Decision Service MCP。工作区建立或岗位任命、交接时，由工作区协调员核任职，在本工作区增量分配决策服务。成员岗位在自己的客户端验证 OAuth。公子于 2026-11-20 确认，已获配并启用决策 MCP 的 Agent 可获得覆盖全部 Multica 项目的有限判断授权，业务调用使用服务端已获准的身份。任务中的具体执行、资源变更和业务验收仍沿原授权办理。

管理员在新建项目、给 Agent 开通或移除决策 MCP 时，同步服务端项目清单与角色凭据。按实际调用身份核对目标项目 UUID 和服务端允许的操作。已启用的挂载证明配置存在，`get_decision` 对未用编号返回 `not_found` 证明该会话可发起只读查询，项目范围另查该身份的服务端授权。共享 OAuth 按其实际授权范围使用。凭据只通过获准的运行时入口加载，工作区 MCP 配置仅引用变量。Hindsight bank 授权单独办理。

### 主动推进与按需决策

接单、原假设失效或准备交付时，依据当前任务授权、原 Issue 和实际 Run 选择下一步。

- **下一步明确时直接做。** 已有清楚的归属、验收条件和唯一可行步骤时，执行、验证并在原卡留证据。
- **缺事实时先查。** 用已授权工具查原卡、Run、产物或权限依据，优先做成本低、可逆、能区分路线的检查。若原任务缺少写权、放行或验收授权，沿原卡找有权补齐的人，并继续不依赖该条件的工作。
- **出现实质取舍时主动用 Decision Service MCP。** 两条以上获准且可行的路线会实质影响交付、风险、资源或返工时，在当前 Run 提供真实项目 UUID、关键证据、约束与候选。输入足够用 `recall: skip`，确需经验才查获准的记忆库。执行者可决定职责内的实现路径。复审者可比较补测和返工路径，复审结论依据验收条件及产物证据。其他岗位可在授权内提出建议，由有采纳权的责任人作决定。
- **按原任务执行、对账和反馈。** 保存稳定的 `request_id` 和候选快照。响应不明先用 `get_decision` 查原请求。复核 `complete + suggested` 的结果与原卡当前状态，记录实际选项和理由，原执行方沿原决定反馈。建议失效、证据不足或服务不可用时，先推进独立就绪项。责任人可在授权内采取可逆措施，仍需决定的事项带推荐项和待补证据交给有权的人。

现有和新增角色启用决策 MCP 时，在自定义 prompt 写入上述触发条件与岗位边界，配套挂载 `decision-service` Skill。更新、换入口或撤销时一并读回 prompt、MCP、Skill 和项目授权。授权范围与角色能力分别记录，用该 Agent 的新 Run 验证直接执行及需要取舍时的建议、实际动作与反馈。

## 一条能执行的指令

G8 或协调员下达指令时写清 **谁、为哪个工作区和项目、要做什么、做到什么算完成、何时向谁回报**。有关联时附原 `job_id`、Issue、Run 或 `decision_id`。无承诺期限可约定事件检查点。

> 示例：请目标工作区协调员在原项目核对失败的 Run，定位首个失败步骤并提交证据引用。能在现有授权内修复时交原执行者处理，再请复审者复核。需要其他工作区的资源时，把两个可行选项、推荐项和影响回给 G8。首次核对结束或出现阻塞时，在原 Issue 和原信箱任务回报。

## 从交办到交付

1. G8 指定目标工作区、项目和原任务。每件事有一个实际派发者。使用当前已验证的交办入口；经信箱交办时保留原 `job_id`。传输超时先查原件和原 Issue。
2. 协调员核对原件，在对应项目回报接手人、Issue、下一步及检查点。信箱保存、工作区接手、Run 开始分别以各自回执确认。
3. 普通进展留在原 Issue。目标、风险、交期或接手人发生实质变化，需要上游决定，达到约定检查点，或已有可验收交付时，主动回报 G8。阻塞报告写明影响、已试过什么、推荐动作和等待谁。
4. 协调员核过实际交付物后沿原任务回报。Task Mailbox 保存版本和摘要，G8 读取该版本；最终验收沿项目授权。新工作区上线时核对协调员身份、所属项目、决策 MCP 的实际调用和一件任务的双向回执。

### G8 经信箱交给工作区协调员

1. G8 从 Task Mailbox 按 `job_id` 读回原件，记录原件状态、`payload_hash`、实例、工作区、项目、现任协调员和稳定 `request_id`，冻结建卡或关联参数。经认证的发件人或获授权操作人显式调用 `dispatch_issue`。网关使用独立只读身份校验原 job 的摘要、范围与回程，并检查现任登记。确认没有原卡或指派时才发起一次建卡和指派。已有唯一原卡时使用 `original_issue_id` 关联。响应超时先查 `get_dispatch` 和原卡，随后沿同一身份、请求 ID 和参数对账。
2. 原卡已关联、经获准的原生 Issue 和 Run 读取确认尚未指派且无相关执行，且本件明确授权启动时，操作人可用 `update_issue` 指派现任协调员一次。保存独立于 `dispatch_issue` 的固定操作 `request_id` 和原生 `expected_revision`，传入 `assignee_type=agent`、`assignee_id` 和 `start_run=true`。已有指派、相关 Run 或写入结果不明时，沿原卡和原操作回执对账，补可验证的接手证据。
3. 接手的协调员在原卡核对原 job、摘要、项目和实际接手人，用自己的原生 Agent 身份写一次顶层静默备注。下面的 JSON 值取自该件，整行写入同一备注。用 `multica issue comment add <issue-id> --content-file <file>`，提交以后按原 Issue 读回。响应丢失时先查备注和原 ID，在证据不足时保留待核，不追加第二条。发件人或网关成员账号提交的备注仅作跟进记录。

   ```text
   /note {"event":"mailbox-intake-v1","job_id":"<job-id>","payload_hash":"<sha256>","issue_id":"<issue-uuid>","coordinator_id":"<agent-uuid>"}
   ```

4. G8 带同一个派发 `request_id`、`job_id` 和原作用域调用 `get_dispatch_acceptance`，核对 `issue`、摘要、协调员，以及 `acceptance.receipt` 的实际作者、原生评论 ID 和服务端时间。已有历史卡且尚无唯一可信绑定时，保留「接单未确认」，由原发件人或获授权操作人记录原卡线索、跟进人及下一个复查时间或事件。权限不足、读取截断、回执歧义时同样处理。恢复沿原登记对账。
5. 回报分别引用四项证据。Task Mailbox 原 job 的 `PERSISTED` 是信箱保存。`acceptance.state=accepted` 是协调员接手。`run.state=started` 带原生 `id` 和 `started_at`，表示同卡同 Agent 处理这笔 job 的 Run 已启动。网关通过原生备注的 `source_task_id` 定位该 Run，随后核验原生运行时间。缺少绑定的同卡 Run 只作候选，`queued` 仍在等待。历史卡通过 `update_issue` 指派时，核对该操作的 `run_outcome` 和可归因的同卡、同 Agent 精确 Run。归因或启动时间缺证时保留待核。指定验收人按交办约定记录业务验收。信箱的 `RESULT_READ_ACKNOWLEDGED` 只记录收件方读取指定结果版本。

## 当前 Issue 的下一步由谁执行

执行者按[主动推进与按需决策](#主动推进与按需决策)核对当前目标、可做的下一步及约定回程。同一原因再次出现时先查变化，再决定是否重试。

遇到局部障碍，原负责人先推进授权内可独立办理的动作，受阻支路沿原线程追证。仅在整卡确无可行动作时建议标记阻塞，记录具名主责、缺项和复查点。暂停、强制审查和看板更新沿用原项目约定。需要公子决定时，带推荐项、影响和最迟决定时间。[原卡解阻闭环](#原卡解阻闭环)

需要另一位责任人接手判断时，先在原卡交接可行选项、推荐及代价、已交付的共同部分，再按项目工作流移交。复盘按同一事项核两项：从原卡首次记录阻塞到第一项可验证的有效动作（如完成区分根因的检查、取得缺失授权或实际恢复）的耗时，以及同一已交或在途动作又被派工的次数。单纯转述、提醒、Run 启动不计作有效动作；缺服务端时点或原件时标待测。

| 当前事实 | 下一步与回执 |
|---|---|
| 委托约定只回原信箱、原卡，且由发起者验收 | 有「回执交付」的项目，建单或交办时直接选择该状态并指定执行者；执行中才确认回程时，沿原卡进入该分支。执行者按原 ID 读回回执后结束 Run，发起者验收并处理终态。普通需独立复审的交付仍走 `in_review`。 |
| 原项目要求独立复审，候选和验收条件已确定 | 执行者提交候选 Run 与产物，进入 `in_review`。通过、可修正失败、已达返工上限均按项目原有规则处理。等凭据、等指定验收人和明确暂停的工作沿原等待条件办理。 |
| 两条以上获准路线都可行，选择会改变交付物、接手人、资源或交期 | 在职责内可决定的取舍就地处理。需要交接时沿原 Issue 向在任项目负责人提出具体选项、依据和影响。未任命负责人时交工作区协调员。已有人承接同一判断时沿同一回合核对。跨工作区取舍由协调员报 G8。 |

项目工作流设有「待决策」时，先在原卡保存执行者、候选动作和目标、验收条件及回程，再单独切换到该状态，由工作流派给已登记的处理人。状态键和处理人从该项目生效的工作流读取。没有此阶段时沿原 Issue 联系负责人。退回执行需同时指定实际执行者，进入独立复审则只改状态。每次移交读回 Issue 和实际启动的 Run。

承接判断的人先在原 Issue 或 Run 记下 `request_id`、候选及依据。调用 `evaluate_decision` 后按原 ID 用 `get_decision` 读回，核对 `complete`、`suggested`、选项仍在原候选内且原状态仍适用。实际执行方沿原任务采用或说明未采用原因，取得可核验的动作和结果后分别用 `record_decision_feedback` 回填 `application`、`result`。给发起者的回执带 `decision_id`、实际选项和原件。反馈未确认时只核对或补传同一事件及修订。服务端按调用身份隔离决定和反馈。需要由另一身份执行并回填时，先沿原卡交候选和证据，由获准执行方以自己的身份请求决定；已经取得的建议沿原决定对账，接手人通过原卡回传执行证据。

回填前核对[反馈的必填字段与验收时点](references/decision-feedback.md)。

## 原卡解阻闭环

每个可独立验收的阻塞事项沿原 Issue、原线程和原委托保留一名主责。同一张卡可以有多条支路。原负责人有能力、有权限，就地办理；已有人接手的同一动作沿原回执续办，新增派发为零。

**首次交办。** 确需他人承接时，由唯一获准派发者直接交给能执行的人。原卡一次写清卡点与证据、目标及版本、允许的操作及停止条件、验收人和所需证据、回程及复查点。能在同一授权内完成的诊断、处置、复验、回证，由主责连续办理。结果未知或已有在途时，沿原检查点或请求 ID 对账。目标、版本或实质动作变化时重新核授权与接手证据。连续处置的中间步骤无需逐步转派。

**协助与换人。** 主责需要专业证据或额外授权时，只向有权人提出具体缺项，自己继续跟进。指定验收人按原范围签认，要求独立复审的工作仍需独立复审。主责确实无法继续、任职变化或任务已实质超出职责时，再由协调员核清旧在途，沿原线程记录换人原因、剩余动作及新主责。原方跟进至新主责的接手回执可读回。G8 兜底解决最小未决事项。

| 已查到的事实 | 谁采取下一步 |
|---|---|
| 方案已定，执行待接手 | 原负责人可自办时在原线程确认本次动作并执行。必须换人执行且无同一动作在途时，按首次交办要求当轮交办一次。执行人待定时由现任协调员具名负责落实，直到实际执行人签收。 |
| 已交办，接手待确认 | 发件人沿原卡核对当前动作的请求、接手备注、送达及原生 Run。到点先对账。仅当确认未收到、无同一动作在途且获准时，由唯一派发者沿原单提醒一次。结果未知或归因不清时沿原标识查证，保留具名跟进人和检查点。 |
| 已接手，约定检查点已到 | 主责核新增证据、在途 Run 与既有提醒，说明剩余动作和下一检查点，区分复查时间与交付承诺。确需跨人协调时，由协调员落实具体对口；只有联系人线索时注明权限待核。 |
| 执行结束，验收证据不足 | 项目负责人核对原候选 Run 和实际产物，指定验收人列已验与缺项。动作已成功只补原回执；需要修正产物才按既有返工规则处理。外部授权或证据缺口交协调员追证。 |

在原线程记录当前事实与原件、下一动作、目标与版本、具名跟进人与有权补证人或待核对口、预期证据、复查点和验收范围。只作记录时用静默备注。同一动作沿用原检查点或原交办请求 ID。具名执行人的原生回执须归属原卡与原线程，并同时匹配本次检查点（或原交办请求 ID）、目标和版本，才计为当前动作接手。交办、送达、Run 启动及协调员承诺落实分别按各自事实记录。新动作使用新检查点，旧回执保留在原记录。独立支路在同一 Issue 的不同原线程分别办理。

已登记腾讯 `unblock` 的动作，由具名执行人用本人身份在原根线程回复静默备注。替换下例的所有占位值；也可用目标已登记的 `request_id` 代替 `checkpoint_id` 和 `step`。协调员读回原生作者、服务端创建时间和评论 UUID，再将 `multica:comment:<评论 UUID>` 及该原件的绑定字段写入核收摘要。

```text
/note unblock.pickup.v1 {"thread_id":"<原根评论 UUID>","checkpoint_id":"<检查点>","step":"<动作>","target_id":"<目标>","target_version":"<版本>"}
```

主责不能取得必要资源或授权时，由协调员协助。查不到有权人、达到最迟决定时间，或同因再次出现且本地已无有效动作时，协调员当轮沿原委托将具体未决事项、证据、建议及下一检查点交 G8。G8 落实补证人或取得有权方的暂停、取消、调整决定，接手须有本人或已授权入口的可读回执。主责继续推进不受该缺口影响的工作。

补件到达后，主责核来源、时效、对象及权限。有实质取舍才结合原件、获准项目 bank 和决策 MCP 选择路线。实际步骤恢复后，登记的项目负责人依据执行者原系统回证签认恢复，指定验收人签认相应范围。已成功的动作只补缺失回执，首件和整卡分别验收。

### 阻塞案例的检索、沉淀与反馈

1. **遇到阻塞，查一次案例。** 项目负责人与协调员先看原线程是否已有本轮检索结果，由一人按受阻步骤和具体现象查当前项目 bank。确有需要时按既有权限跨项目只读。读回最相关的原文，用本次原件核对适用条件、版本和权限，选能区分原因的最小检查。未命中、bank 不可用或条件不符时，继续查本次原件；出现新的症状或证据再检索。历史放行仅限原范围。
2. **动作已验收，由知识管理员异步整理。** 对重复出现、排查代价高或涉及关键授权的阻塞，协调员在原线程标明具体动作、验收范围、验收人和证据，沿原卡交现任知识管理员。知识管理员先按原 Issue、动作、现象和来源查重，记录现象、最小检查、已证根因或未明之处、有效动作及所需授权、验收证据、失效条件。只完成定位的事项可保留为诊断经验，恢复需另有回证。原文已覆盖本次结论时直接引用 bank 和文档 ID；有实质增量才按原文档维护权限补订，无匹配且确有价值时才在获准的当前项目 bank 新建。写后按原 ID 读回；异步结果未知时沿原操作对账。业务验收、推进和关卡沿原约定办理，知识整理不占用其检查点。
3. **用过案例，实际执行人回一句。** 在使用该经验的原 Issue 线程记录文档 ID、做了哪项检查、实际结果和证据，以及适用或不适用的原因。协调员给代办执行人交办时带上这项回报要求。发现同症异因或条件已变，知识管理员据反馈补区分方法、有效版本或失效条件；历史试点演练标注演练范围。每轮巡查沿用已有材料，只有新的证据差异才重新交办整理。

需要复核文档摘要时，按原 ID 直接读取完整结构化响应中的 `original_text`，对原样 UTF-8 字节计算 SHA-256。工具只给预览、截断文本或转录副本时，注明可见范围与实算待核，保留原记录。

任命或换任协调员、项目负责人及知识管理员时，将本节中各自承担的动作写入岗位 prompt，并读回实际配置。
