# G8 与工作区协调员职责和协作规范

## 谁负责什么

以所属 Multica 项目看板和原 Issue 核对目标、负责人、进展与验收；执行看原 Run，产物可引用固定提交或附件。旧看板仅供追溯，映射不清先查原件，避免平行建卡。普通项目按当前任务授权办理，业务许可、技术能力、运行事实和验收结论分别取证。按目标工作区的现任登记找协调员（cloud-work 为 Mike，岗位键 `mika`）；换任、同名或归属不清时先核身份。

| 角色 | 职责 |
|---|---|
| G8（云端 Dot） | 统筹跨项目目标、优先级和资源，明确验收人，默认兜底解阻。跨工作区选一位牵头协调员，向公子报需拍板的最小事项。 |
| 工作区协调员 | 接单、落实具名执行者，按项目要求安排复审，在授权内决定实施路线、协调跨人资源，追到接手有据，沿原委托回报。 |
| 项目负责人 | 推进项目内的路线、分工、集成与约定验收；不能在本项目解决的取舍带建议交协调员。 |
| 执行者、复审者、验收人 | 执行者交实际结果和证据；复审者按项目要求独立复核；指定验收人签认明确范围。 |

G8 已认证账号按公子确认的范围拥有 Task Mailbox 现有及后续项目的最高业务读写和操作权限，可向各工作区现任协调员交办；业务执行与放行沿该任务授权。

## 从交办到交付

### 一条能执行的指令

沿原 Issue、原线程及原委托写清：具名主责、动作与目标版本、已知事实和在途、授权范围及停止条件、预期产物、验收人、回程与复查点。原负责人能处理就地办理；需要别人承接时由唯一获准派发者交办一次。普通进展留原卡；风险、目标或接手人实质变化、到复查点或已有交付时沿约定回程汇报。

### G8 经信箱交给工作区协调员

沿原 `job_id` 核发件来源、摘要和作用域；用稳定请求关联唯一原卡，响应未知先对账。信箱落盘、具名接手、Run 启动、业务验收分别取证。需要网关识别接单或腾讯 `unblock` 自动核收时，执行[原生回执协议](references/native-receipts.md)，使用相应精确备注；普通项目按原任务回件。新工作区或岗位换任时，协调员核任职并增量分配已准决策服务；新工作区用一件任务验双向回程。

## 当前 Issue 的下一步由谁执行

| 当前情况 | 原卡怎么处理 |
|---|---|
| 已有主责、方案可执行 | 同一授权内连续诊断、处置、复验和回证。普通任务可在一条原生回件中分述谁接了本次动作、做了什么、实际结果和证据。只作记录时用静默备注。 |
| 确需换主责 | 核旧在途、已完成部分和剩余动作，原方跟到新主责在原线程对当前目标、版本及检查点或原请求签收。执行人待定时由协调员具名落实。结果未知沿原 ID 对账；只有确认未收到、无同一动作在途且已获准时才提醒一次。 |
| 确需另一有权人判断，或项目要求单独跟踪该决定 | 保存现任执行者、候选及目标、验收条件和回程。有「待决策」阶段时读生效配置、切换一次；无该阶段沿原卡交有权人。主责能决定且无单独跟踪要求时留在当前 Run。移交读回 Issue，仅在预期派发时核实际 Run；排队、未知按原号跟进。 |
| 需独立复审或返工 | 指明候选 Run 与产物，按原项目进入 `in_review`、返工或到达返工上限的处置。转审只改状态，退回执行时明确实际执行者。仅修正受影响部分。 |
| 发起者验收，工作约定只回原卡或原信箱 | 项目设有「回执交付」时按此分支交办，发起者核结果并处理终态。回程故障时在原卡留获准披露的产物引用或证据、原标识、具名跟进人和恢复条件，执行 Run 可结束。回执本身是交付物时该项仍待交付；恢复后先对账，确认缺失才补送。 |

## 原卡解阻闭环

### 阻塞补证与续办

每个能独立验收的阻塞保留一名主责。新增补证、转派或开 Run 前，先核原件、已有证据及在途，回答：**缺什么，影响哪个动作？查到后做什么？查不到由谁决定或等什么条件恢复？** 新增前置条件须有原授权、验收要求或实际系统约束作依据。

- 主责可在权限内核清的，当前会话直接检查并续办。只能在实际执行会话取得的身份、环境或版本证据，在该会话获准的检查步骤中取得。两种结果都不改变处置、原约定也无此要求时，跳过该检查，直接办已有授权的下一步。
- 缺专业证据或许可时，只向有权人提具体缺项；事前审批、必要安全控制及独立验收沿原约定。缺许可仅暂停受影响动作。同卡独立支路分别沿原线程推进；整卡确无可行动作时才建议标阻塞。
- 到复查点先对账。没有新事实、没有有效动作时，保留主责、恢复时间或可观察事件，每轮巡查照常汇报。查不到有权人、已到最迟决定时间或同因反复且本地无有效动作时，协调员沿原委托交 G8 具体缺项、影响、建议和下一检查点，跟到 G8 本人或获准入口确认接手。G8 落实对口或取得暂停、取消、调整范围的决定。
- 主责凭实际 Run、产物及当时有效授权报告恢复，普通项目复用原约定的有效签认；已登记自动核收的事项按协议签认。仅首件通过就记录首件；目标、版本或实质动作改变后核新检查点及接手依据，保留历史回执。

复盘只看两个数：首次记录阻塞至首个可验证有效动作的耗时，以及同一已交或在途动作被重复派工的次数。转述、提醒和 Run 启动另计；原件不足标待测。

### 阻塞案例的检索、沉淀与反馈

负责人或协调员由一人按新症状查已授权项目 bank，对照原件做最小检查。已有查询可复用；未命中或服务不可用时继续现场核验，无新线索不反复查询。跨项目仅按授权读取。

具体动作验收后，反复出现、排查成本高或涉及关键授权的案例，由协调员沿原卡交现有知识管理员异步整理。记下症状、最小检查、已证原因、有效动作及所需授权、验收证据和失效条件。诊断与恢复分别留证。同一来源已覆盖就引用原文档 ID，有实质增量才按权限补订。新建限获准的当前项目 bank；写后按原 ID 读回，异步未知沿原操作对账。校验正文用完整结构化 `original_text` 的原样 UTF-8 SHA-256，预览截断则注明待核。执行人在用例原卡回一句案例 ID、检查、结果及适用性；知识整理不占业务验收检查点。

## 怎样快速判断

### 主动推进与按需决策

明确且已授权的下一步直接做。两条以上获准路线会实质改变交付、风险、资源或返工时，按职责用 Decision MCP，以真实项目 UUID、原始证据、约束和有限候选作判断。资料足够用 `recall: skip`。辅助服务不可用时，有决定权且原件充分的主责可就地判断；项目明定的工具审批仍须完成。缺授权的具体事项交有权人，独立就绪项继续。

沿原卡保存稳定 `request_id`，用 `get_decision` 核对 `complete`、`suggested`、原候选与当前状态。实际执行方记录采用或未采用的理由，按实际动作与结果分别回填 `application`、`result`。调用身份隔离时由有权的原调用方依执行证据回填；未知沿原决定、原事件与修订对账。[反馈字段及跨身份回程](references/decision-feedback.md)

G8、现任协调员和已确认的项目负责人默认获准使用 Decision MCP；已获配并启用的角色可按公子确认的政策获授全部 Multica 项目的有限判断权限，调用前核实实际身份的服务端项目范围。新建项目或调整挂载时，管理员同步实际角色身份和服务端项目范围；客户端 OAuth、服务端权限、项目 bank 与业务许可分别核对。凭据只经获准运行时入口加载。已启用挂载或查询未知编号得到 `not_found` 只证明对应层级。给角色启用决策能力时挂载适用 Skill，prompt 写清职责和触发条件；任命、换任或撤销时读回配置与授权，新 Run 核直接执行及按需决策的实际结果。协调员、负责人及知识管理员的 prompt 同步各自的解阻与案例职责。
