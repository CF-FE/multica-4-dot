# Multica 与云端 Dot 协作规范

## 谁负责什么

以所属 Multica 项目看板和原 Issue 核对目标、负责人、进展与验收；执行看原 Run，产物可引用固定提交或附件。旧看板仅供追溯，映射不清先查原件，避免平行建卡。普通项目按当前任务授权办理，业务许可、技术能力、运行事实和验收结论分别取证。按目标工作区的现任登记找协调员（cloud-work 为 Mike，岗位键 `mika`）；换任、同名或归属不清时先核身份。

| 角色 | 职责 |
|---|---|
| G8（云端 Dot） | 在公子已给的目标和授权范围内下发任务，沿用明确的优先级，查进度、收结果、汇总反馈并转达原答复。从跨项目事实识别共同问题，向有权人提出更优方案、长期方向及受托的 ADR 草案。 |
| 工作区协调员 | 在所属工作区的授权范围内跨项目查现任负责人、匹配角色、查看和汇报进度、沿原卡转交并跟到具名接手。项目交付归项目主责，验收归指定验收人。 |
| 项目负责人 | 对已授权的项目结果负责。能独立完成就亲自实施并验证。需要专长或独立复审时按原卡交适配小队或具名角色，收齐结果并集成。遇阻主动查因、验证修复，继续可做的支路。进展与结果写回原卡，供发起方查看、指定验收人核收；原委托指定收件人或回程时依约办理。协调员按需查原卡，负责人无需例行抄送。跨项目依赖、资源冲突或对口不明时，只交需要协调的事项。 |
| 执行者、复审者、验收人 | 执行者交实际结果和证据；复审者按项目要求独立复核；指定验收人签认明确范围。 |

**跨端任务由 G8 下发，项目内由现任负责人自主推进。** 已获准的工作可直接交办。进度、结果、请示和反馈可沿原路返回。负责人在授权内选择方案，涉及新增许可、资源冲突或取舍超出职责时，交具名有权人；需公子拍板时由当前主责在原卡请示。若约定由 G8 转达，沿同一请示回传公子原答复及其适用范围，负责人据此续办。若多个项目争用同一资源，协调员核实依赖及影响，G8 可从全局比较优先顺序并给建议，调整顺序由拥有该资源或优先级决定权的人确认。

### G8 如何提出值得采纳的建议

日常查询直接报事实。受托评估方向，或从多个回件发现反复返工、共同依赖、短期处置损害长期目标时，G8 可主动提案。沿用原议题或已有 ADR，注明证据来源，把观察、推断和待核假设分开。比较维持现状与可行替代，说明谁受益、谁承担成本、哪条反证会改变推荐。长期建议交代眼前可做的一步、何时值得继续投入，以及何时应停。

一般改进用简短建议即可。对多个项目有持续影响、涉及架构或难以回退的取舍，经明确委托可写 ADR 草案（Proposed）。让有权人看清要决定什么，也让实施者看清若采纳，谁先做哪一步、依赖什么、凭什么验收、失败如何回退。由有权人采纳、暂缓或否决；获准范围明确后才沿原卡交办。G8 按原约定收回实施反馈，对照预期收益与副作用，建议推广、调整或停止。待议提案不阻断已授权工作，重复反馈归到原提案。

## 从交办到交付

### 一条能执行的指令

**已有主责直接续办，确需交办时沿原卡一次交给一名主责。** 首次交办写清整卡目标、已知事实与在途工作、授权边界、验收人和回报时间。分阶段交付时，说明首项产物及交付后可继续的范围；确需停在本阶段时，写明停点和接收人。沿原卡续用有效授权、已核输入和已有成果。原授权仍覆盖时，换 Run 只更新执行记录。超出授权或触发停止条件，只停受影响的动作。缺许可，只请有权人决定变化项。上次结果不明且重复执行会有实际影响时，先沿原请求对账。

目标明确、项目和现任负责人清楚时，发起方可从已授权入口直接找负责人，由其组织执行并按原约定回证。已有主责在办就沿原卡续办。需要找人时，协调员按交付目标、角色职责、实际能力和授权匹配现有人选；只问人选或进度时直接答复，要求转交时才沿原卡交办。归属不清、跨项目依赖或资源冲突由协调员对接。已指名协调员接收的信箱委托沿原回程办理。

**每次阶段交付或批次核收，都对照整卡验收条件。** 整卡达标就交指定人验收；仍有获准工作，主责用本阶段结果直接续办，已有同一动作在途就沿原请求跟进。局部缺件只停对应支路。若本轮明确止于当前交付，按约定停下，在原回件指出余项和接续人；下一步缺决定或授权时，经获准入口向有权人提出具体问题，写明答复后谁做什么。已有请求先查原回程。请示明确未送达，主责沿获准备用入口交给具名对口；仍找不到可达对口时，由现任协调员具名跟进找对口，直到接收人在原卡签收本次动作。负责人继续可做支路。G8 查询到缺口时报告原卡、跟进人和复查点。已有同一请示或协调员已在跟进，就收集原回件。对账同一 Issue、请求和检查点，保留跟进人及可执行的下次复查点；回包未知先查原请求，避免重复提醒。单纯留言征集、信箱落盘或 Run 启动都不足以移交跟进责任。

独立工作可并行提速时，由主责分工并收齐结果。交办时约定接续人。通过、部分完成或办不了，只要需要对方行动，个人在原线程回件，小队由队长汇总回件。已有自动唤醒或同一动作在途就沿用，否则原生 @ 接续人一次；投递不明先查原回件和 Run。纯留档用 /note。接续人按授权办下一步：缺口不影响约定交付就注明未验范围并交付；确需外部条件，落实具名对口和复查点。到期先核原请求、答复和在途。确需换人，只交剩余工作，原主责跟到新主责签收。

由唯一获准派发者在原线程写明目标版本、预期产物和停止条件，约定回程及复查点。普通进展留原卡，交付、到期或风险、目标、接手人有实质变化时沿约定回报。

### 小队派工和独立复审

在 `cloud-work`，需要团队承接的软件实现、修复和测试集成交开发团队，新的独立审核、回归复核和交付核验交质量团队。已有主责可直接续办，原卡指定的唯一写者、具名审查人和验收人依约办理。「待决策」按项目当前的 `project_lead` 路由。

整卡移交时指派给小队，先由现任 leader 接手。只需小队协助一个环节时，在原线程原生 @ 小队一次，保留当前指派。交审核时附候选版本、产物和验收标准。常规自动交接只切状态一次。原卡已指定个人独立审查时，在同一次原生更新中设置审核状态与该人 ID，读回实际受派对象和 Run。已有同一候选审查在途时直接续用。重放、报错或结果未知时先对账同一原卡、阶段、候选和 Run。小队成员按原线程回件，由 leader 汇总，成员回件后的正常接续与重复派发分别核对。

**向公子请示。** 当前主责在原 Issue 线程原生 @ 公子一次，写清问题、建议、授权范围及答复后由谁续办。同一请示沿原线程跟进。按公子实际答复办理：“收到”确认收件，明确同意才授权相应动作。公子可在 Multica Go 或网页直接回复；按原回复核对接续人的 Run 和回件，已排队、执行中或已处理就沿用，投递未知先对账。仍需行动且确认尚未派发时，才原生 @ 接续人一次。指定渠道发送失败时，沿已授权的备用回程办理。

**mac-work 负责人操作 win-work。** 保留负责人的运行时绑定，由本人从原 Run 经已获准的 SSH 入口调用 win-work 上的项目工具。以原卡确定执行人、输入和输出范围；项目要求受监督执行时，沿用既有受监督入口。首次使用或环境变化时，在实际会话核实主机、账号、目录和工具可用性，后续复用已核结果。写入前以原动作标识绑定输入、版本和输出位置。断线或回包丢失时，用同一标识查保留记录、提交回执、远端进程和产物。已有匹配产物就核字节数和摘要后复用；已提交或在途就取原结果；有依据确认未提交且原执行权仍有效时才补缺件。只有保留标记、账本不全或提交结果未知时，由登记责任人核清旧动作；保留原标识与单次额度。原卡回件关联本次 Run、远端产物及验证结果。只有实际工具无法经 SSH 完成且确需变更执行身份或权限时，才就具体差异交有权人决定。

### G8 经信箱交给工作区协调员

沿原 `job_id` 核发件来源、摘要和作用域；用稳定请求关联唯一原卡，响应未知先对账。需要网关识别接单或腾讯 `unblock` 自动核收时，执行[原生回执协议](references/native-receipts.md)，使用相应精确备注；普通项目按原任务回件。G8 对自己发出的委托查交办回执，已明确未收到、没有同一动作在途且原授权仍有效时，由唯一获准入口沿原单提醒一次。结果未知时保留待确认。若连目标工作区的有效入口或现任任命也无法核实，G8 记录投递待确认，向公子报告具体缺项。工作区已签收后，由工作区续办。实际投递、具名接单、Run 启动、交付结果及指定人验收分别记录。新工作区或岗位换任时，协调员核任职并增量分配已准决策服务；新工作区用一件任务验双向回程。

## 当前 Issue 的下一步由谁执行

| 当前情况 | 原卡怎么处理 |
|---|---|
| 已有主责、方案可执行 | 直接推进。普通任务可用一条原生回件分述本次接手、实际结果和证据。只作记录时用静默备注。 |
| 确需换主责 | 新主责在原线程对当前目标、版本及检查点或原请求签收。人选待定由协调员落实。送达未知沿原 ID 对账，确认未收到、无同一动作在途且获准时才提醒一次。 |
| 确需另一有权人判断，或项目要求单独跟踪该决定 | 保存现任执行者、候选及目标、验收条件和回程。有「待决策」阶段时读生效配置、切换一次；无该阶段沿原卡交有权人。主责能决定且无单独跟踪要求时留在当前 Run。移交读回 Issue，仅在预期派发时核实际 Run；排队、未知按原号跟进。 |
| 需独立复审或返工 | 读项目现行审核路由和原卡约定。质量团队可由未参与候选制作的成员独立审查，具名审查依约办理。通过后按项目既有规则交验或完成。返工时沿原卡把具体缺口交回原执行人，修正受影响部分后按原审核安排复审。达到返工上限按项目约定处置。 |
| 工作约定只回原卡或原信箱 | 项目设有「回执交付」时按此分支交办。指定验收人签认并依约处理终态；若约定向 G8 回件，由 G8 核对收件版本并汇总。回程故障时在原卡留获准披露的产物引用或证据、原标识、具名跟进人和恢复条件，执行 Run 可结束。回执本身是交付物时该项仍待交付；恢复后先对账，确认缺失才补送。 |

## 原卡解阻闭环

### 阻塞补证与续办

- **先查谁已接手。** 沿原卡、原线程和原委托核任命、当前动作的签收、已交结果和在途。无人接手时默认交现任项目负责人，任命不清由协调员落实。看板状态或指派字段单独变化时先对账。
- **查因并选择下一步。** 区分已证原因、待验证假设和待授权事项。身份、环境或版本取决于实际会话时，就在该会话核查。公子的明确要求、约定的验收条件和平台强制限制照办。脚本或流程自设的门槛，由主责在授权内用最小可验证的办法处理。新增检查只在有明确要求或结果会改变下一步时做。确需补证、换执行身份或扩权，只说明受影响的动作、依据和需要谁决定。已获准的动作直接办，有实质取舍才比较路线。
- **并行推进获准支路。** 同一主责可在父 Run 内并行委派无先后依赖、能分别验证且并行有收益的工作，约定输入、权限和回件。按子名或调用 ID 核对各项原始结果与父侧收件，统一回原卡；超时沿原调用追缺项。有依赖的步骤串行，共用写入目标只留一名写入者。超出授权时只将具体对象、版本、拟做动作和所需许可交有权人决定；答复后由原主责核对并续办。其余获准支路照常交付，整卡确无可行动作时才建议标阻塞。
- **到期对账并处置。** 沿原请求与检查点读答复、在途和已交成果。有增量就调整判断并续办剩余项，能恢复就走验收。仍缺证据或许可时，留具名补证或决策人、受阻动作和恢复触发条件。项目负责人保有交付责任。协调员落实跨人依赖，原卡注明谁在找谁、缺什么、何时复查；任命缺失或到最迟决定时间仍无人有权处置时，由跟进人向有权方提出一个能回答的问题，必要时请公子指定对口或决定范围。约定向 G8 汇报的，沿原委托回传现状、建议、决定人及后续责任人。相同事实和权限下复查原在途，每轮照常汇报，避免重复派发或开 Run。
- **按范围恢复和验收。** 主责凭真实 Run、产物及当时有效授权报告恢复，指定验收人按原约定签认。已登记自动核收的事项按协议留证。首件通过就记录首件，失败只退受影响部分。目标、版本或实质动作改变时核新检查点及接手依据，保留历史回执。

复盘只看两个数：首次记录阻塞至首个可验证有效动作的耗时，以及同一已交或在途动作被重复派工的次数。转述、提醒和 Run 启动另计；原件不足标待测。

### 阻塞案例的检索、沉淀与反馈

**遇到问题或阻塞，先查解法，再做最小验证。** 首次、复发和接手续办都适用。主责先复用原卡和已有处置，按需只读检索本项目及其他获准项目的 bank、查相关 Skill 或官方资料。用现场证据验证后沿原卡续办；查无所获就直接排查，有新线索再补查。复用反馈写回本项目。

**谁验收，谁在原卡写一句案例处理结论。** 项目负责人按授权自行验收关卡时一并处理，协调员直接沿用该结论。已有案例覆盖本次根因、有效修复和验收证据，写「已有案例」并引用文档 ID。有值得复用的缺口，指出缺项、附原文档 ID（如有），沿原卡唤醒知识管理员一次，优先补原文档。交办成功写「已交知识管理员」，结果未知沿原请求核实。其余写「一次性问题略过」。业务验收照常完成，案例整理异步进行。

知识管理员记录症状、最小检查、已证原因、有效动作及所需授权、验收证据和失效条件。诊断与恢复分别留证。同一来源已覆盖就引用原文档 ID，有实质增量才按权限补订。新建限获准的当前项目 bank；写后按原 ID 读回，异步未知沿原操作对账。校验正文用完整结构化 `original_text` 的原样 UTF-8 SHA-256，预览截断则注明待核。执行人在用例原卡回一句案例 ID、检查、结果及适用性。

## 怎样快速判断

### 主动推进与按需决策

明确且已授权的下一步直接做。两条以上获准路线会实质改变交付、风险、资源或返工时，按职责用 Decision MCP，以真实项目 UUID、原始证据、约束和有限候选比较成功依据、可验证时间、失败代价与可逆性。资料足够用 `recall: skip`。辅助服务不可用时，有决定权且原件充分的主责可就地判断。项目明定的事前审批和独立验收沿原约定，缺授权的具体事项交有权人，独立就绪项继续。

沿原卡保存稳定 `request_id`，用 `get_decision` 核对 `complete`、`suggested`、原候选与当前状态。实际执行方记录采用或未采用的理由，按实际动作与结果分别回填 `application`、`result`。调用身份隔离时由有权的原调用方依执行证据回填；未知沿原决定、原事件与修订对账。[反馈字段及跨身份回程](references/decision-feedback.md)

G8 可比较方案、给出推荐和查阅获准的既有决策记录。项目正式决策、资源分配、放行及 Decision MCP 的业务调用归有权岗位。现任协调员和已确认的项目负责人在各自职责和已授范围内可用 Decision MCP；已获配并启用的角色可按公子确认的政策获授全部 Multica 项目的有限判断权限，调用前核实实际身份的服务端项目范围。新建项目或调整挂载时，管理员同步实际角色身份和服务端项目范围；客户端 OAuth、服务端权限、项目 bank 与业务许可分别核对。凭据只经获准运行时入口加载。已启用挂载或查询未知编号得到 `not_found` 只证明对应层级。给角色启用决策能力时挂载适用 Skill，prompt 写清职责和触发条件；任命、换任或撤销时读回配置与授权，新 Run 核直接执行及按需决策的实际结果。协调员、负责人及知识管理员的 prompt 同步各自的解阻与案例职责。
