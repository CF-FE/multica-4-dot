# G8 与工作区协调员职责和协作规范

公子于 2026-11-20 确认。G8 统筹跨项目工作，拥有 Task Mailbox 全部现有和后续项目的最高业务读写与操作权限，可以向任何 Multica 工作区的现任协调员发送指令和任务。此默认授权跟随 G8 已认证账号。新增项目沿用同一规则，接入新工作区时登记当地协调员。

## 谁负责什么

| 角色 | 决定与交付 |
|---|---|
| G8 | 明确目标、优先级、资源取舍和验收人。项目或工作区之间出现冲突时，选定方案，给受影响的协调员下达一致的指令，向公子汇报结果或需要公子决定的事项。 |
| 工作区协调员 | 按目标工作区和当前任职登记接单，在所属项目创建或关联原 Issue。选择执行者、安排复审，在任务授权范围内决定实施路线，处理可就地解决的阻塞，向 G8 交付带证据的结果。 |
| 项目负责人 | 负责本项目的路线、分工、集成和约定的业务验收。用决策 MCP 比较会影响交付的可行选项，给执行者明确指令。跨项目资源冲突、目标或交期需调整时，带推荐方案报工作区协调员。 |
| 执行者、复审者与验收人 | 执行者提交产物和复现证据，复审者核对约定范围，指定验收人记录业务结论。运行事实引用原生 Run，读确认由实际收件方出具。 |

按 `workspace → 当前协调员 → project → Issue/Run` 找人和定位任务。例：`cloud-work` 的现任协调员是 Mike，内建岗位键为 `mika`。其他工作区从自己的原生登记解析。发生同名、换任或绑定冲突时，先核实该工作区的实际任职，再派该件。跨工作区任务由 G8 选一个牵头协调员，其他协调员分别接有明确边界的子任务。

## 怎样快速判断

G8、各工作区协调员及已确认任职的项目负责人默认获准使用 Decision Service MCP。工作区建立或岗位任命、交接时，由工作区协调员核任职，在本工作区增量分配决策服务。成员岗位在自己的客户端验证 OAuth。Multica Agent 以各自的独立服务身份调用，按公子 2026-11-20 确认的范围，所有已获配并启用决策 MCP 的 Agent 均可为全部 Multica 项目作有限判断。任务中的具体执行、资源变更和业务验收仍沿原授权办理。

管理员在新建项目、给 Agent 开通或移除决策 MCP 时，同步服务端项目清单与角色凭据。原生项目 UUID 用作决策请求的 project_id。凭据只随该 Agent 的 Run 注入，工作区 MCP 配置仅引用变量。Hindsight bank 授权单独办理。用该 Agent 的真实 Run 核验建议、实际动作与反馈。

- **规则能决定的事直接做。** 已有清楚的归属、验收条件和唯一下一步时，协调员执行并留痕。逐步上报会增加等待，事事等 G8 容易使工作区停在可自行解决的问题上。
- **有实质取舍时主动用 Decision Service MCP。** 例如两个可行路线竞争同一资源，或“继续、返工、升级阻塞”都会改变交期。先筛除越权和不可行选项，把目标、证据、约束、候选及参数交给 `evaluate_decision`。输入足够用 `recall: skip`，确需经验才查获准的记忆库。
- **由有责任的人作决定。** 保存稳定的 `request_id` 和候选快照。响应不明用 `get_decision` 找回。对 `complete + suggested` 的结果复核当前状态，明确采用的动作和理由。建议失效、证据不足或服务不可用时，责任人在权限内选可逆方案并说明依据；涉及跨工作区冲突或超出授权时，带建议和待决项升给 G8 或公子。实际采用和结果由原执行方沿原记录回填 `record_decision_feedback`。

## 一条能执行的指令

G8 或协调员下达指令时写清 **谁、为哪个工作区和项目、要做什么、做到什么算完成、何时向谁回报**。有关联时附原 `job_id`、Issue、Run 或 `decision_id`。无承诺期限可约定事件检查点。

> 示例：请目标工作区协调员在原项目核对失败的 Run，定位首个失败步骤并提交证据引用。能在现有授权内修复时交原执行者处理，再请复审者复核。需要其他工作区的资源时，把两个可行选项、推荐项和影响回给 G8。首次核对结束或出现阻塞时，在原 Issue 和原信箱任务回报。

## 从交办到交付

1. G8 指定目标工作区、项目和原任务。每件事有一个实际派发者。使用当前已验证的交办入口；经信箱交办时保留原 `job_id`。传输超时先查原件和原 Issue。
2. 协调员核对原件，在对应项目回报接手人、Issue、下一步及检查点。信箱保存、工作区接手、Run 开始分别以各自回执确认。
3. 普通进展留在原 Issue。目标、风险、交期或接手人发生实质变化，需要上游决定，达到约定检查点，或已有可验收交付时，主动回报 G8。阻塞报告写明影响、已试过什么、推荐动作和等待谁。
4. 协调员核过实际交付物后沿原任务回报。Task Mailbox 保存版本和摘要，G8 读取该版本；最终验收沿项目授权。新工作区上线时核对协调员身份、所属项目、决策 MCP 的实际调用和一件任务的双向回执。

## 当前 Issue 的下一步由谁执行

执行者在接单、原假设失效和准备交付时，核对当前目标、可做的下一步及约定回程。已知规则给出唯一路线时直接执行。缺少事实时，先做一项成本低、可逆且能区分路线的检查，如查原 Run 或核对指定文档。同一原因再次出现时先查变化，再决定是否重试。

遇到局部障碍，先交付各方案都需要、在原授权内且不依赖该障碍的工作。需要独立接手或跟踪时再拆子任务。只有剩余交付都依赖外部条件，或原有暂停、强制审查规则要求停止时，才停在原卡。记录已完成什么、所缺条件、解除责任人和恢复时的第一步。可观察的 Run 终态或子任务完成可用一次对应事件唤醒；人工授权写明等待谁。需要公子决定时，带推荐项、影响及已有的最迟决定时间。

有实质取舍时，有权限和工具的负责人在当前 Run 选择并执行。需要另一位责任人接手时，先在原卡交接可行选项、推荐及代价、已交付的共同部分，再进入「待决策」。服务响应不明时按原请求对账，继续其他独立工作。业务动作已经成功而反馈失败时，仅补同一反馈。复盘以首次发现障碍到下一项有效动作的时间、同因无效重试或重复派工次数、原验收项的实际结果为依据。

| 当前事实 | 下一步与回执 |
|---|---|
| 委托约定只回原信箱，或由发起者核验后处理状态 | 按约定交付。信箱任务读回原 job 的结果版本和摘要，由指定验收人处理后续状态。仅当委托或项目流程要求独立复审时才转 `in_review`。 |
| 原项目要求独立复审，候选和验收条件已确定 | 执行者提交候选 Run 与产物，进入 `in_review`。通过、可修正失败、已达返工上限均按项目原有规则处理。等凭据、等指定验收人和明确暂停的工作沿原等待条件办理。 |
| 两条以上获准路线都可行，选择会改变交付物、接手人、资源或交期 | 执行者或审查员沿原 Issue 向在任项目负责人提出具体选项、依据和影响。未任命负责人时交工作区协调员。已有人承接同一判断时沿同一回合核对。跨工作区取舍由协调员报 G8。 |

项目工作流设有「待决策」时，先在原卡保存执行者、候选动作和目标、验收条件及回程，再单独切换到该状态，由工作流派给已登记的处理人。状态键和处理人从该项目生效的工作流读取。没有此阶段时沿原 Issue 联系负责人。退回执行需同时指定实际执行者，进入独立复审则只改状态。每次移交读回 Issue 和实际启动的 Run。

承接判断的人先在原 Issue 或 Run 记下 `request_id`、候选及依据。调用 `evaluate_decision` 后按原 ID 用 `get_decision` 读回，核对 `complete`、`suggested`、选项仍在原候选内且原状态仍适用。实际执行方沿原任务采用或说明未采用原因，取得可核验的动作和结果后分别用 `record_decision_feedback` 回填 `application`、`result`。给发起者的回执带 `decision_id`、实际选项和原件。反馈未确认时只核对或补传同一事件及修订。

回填前核对[反馈的必填字段与验收时点](references/decision-feedback.md)。
