## 由项目负责人推动下一次有效动作

每个独立卡点都要尽快有一个能改变交付结果的动作。项目负责人默认对项目内解阻负责，已有执行人能办就继续办。沿原 Issue、原线程和原委托跟进。岗位、日常办理口径和原生回执入口以 Skill 为准。[workspace-coordination](../skills/workspace-coordination/SKILL.md#原卡解阻闭环)

### 用 CLOU-40 找断点

11 月 23 日 09:57（北京时间）只读核对时，CLOU-40 的看板状态是 `blocked`，指派人为 Mike。07:56 的原生回件显示，现任凡人项目负责人已经具名接手，准备了启动器候选 r3，并做了静态核对。另一支路缺少现行生产导入实例的获准读取入口和具名保管人，负责人约定 08:15 或原件先到时复查，由 G8 核收。到核对时，原卡上最后可见的仍是这条回件。其他渠道是否办理、生产隔离是否生效，不能由原卡沉默推定。[负责人原卡回件](http://10.207.56.3:3000/cloud-work/issues/01a1f9b0-ab24-7cf1-b748-8b5dc2c4e966#comment-01a205b1-00b7-7021-a5ff-537eae735534)

这个案例暴露了两种误判。按看板指派字段再次派给负责人，会重复他已接下的工作。把“候选已备”和“生产隔离待核”统称为整卡无进展，会掩盖已交付的部分。到了复查点，先查谁能使余下那一步发生变化。按现行分工，项目负责人复查并保留业务主责，协调员协助定位有权保管人，替代路径或范围调整由有权人答复。G8 沿原回程收取已有结果、缺项和处置进展。重复静态审查 r3 或换人重查同一目录都补不上生产端的缺口。

### 一个阻塞怎样走到出口

| 时点 | 主责的动作 | 这一轮的出口 |
|---|---|---|
| 首次发现 | 读原线程、当前项目负责人、具名接手和在途动作，圈定受影响的交付。有胜任执行人时原地续办；无人接手时默认沿原卡交给现任项目负责人一次。任命缺失、换任或确需跨人资源时由现任协调员落实，跟到新主责签收。 | 原卡上找得到本次谁在办、下一步做什么。仅缺一个支路的条件时，其余已获准工作继续。 |
| 判断原因、选择动作 | 用原件区分已证原因、待验证的推测和真实授权缺口。已知且获准的修复直接做；原因不清，先做一次会改变下一步的最小检查。有多个获准路线确实影响交期、风险或返工时，结合相关项目案例、原始证据和 Decision MCP，比对成功依据、最快可验证结果、失败代价与可逆性。 | 选一条当前最有依据的路，写清什么结果会支持或推翻它。能安全恢复交付时先恢复，深层根因有价值再追。缺少数据时保留不确定性。 |
| 执行与并行 | 单一动作由原主责直接办。两个可独立验证且同时做能节省等待的支路，可在同一父 Run 内委派原生子智能体，例如一支核输入、一支验候选输出。共享写目标或有先后依赖的动作串行。父角色掌握授权、保留唯一写入者，按子名或调用 ID 核收各份原始结果，汇总回原线程。 | 有可复验的产物、被排除的假设或具体缺项。已回的独立支路可继续；超时的一支先按原调用对账，取得其结果前保留待核。[四种 harness 的收件方法](harness-role-guide.md#win-work-同一-run-内的原生子智能体) |
| 结果返回或检查点到期 | 有新事实就修正判断，只处理剩余部分。一次失败若排除了某个原因，可换有依据的路线。到期先沿原请求查答复及在途。仍有缺口时，由原主责追具名依赖，协调员落实对口，需要决定时把具体问题交有权人。 | **继续执行、等待具体条件、请有权人决定、提交验收**。等待保有责任人和复查点。有云端回程约定时，G8 按同一委托归集当前结果和缺项。 |
| 恢复、验收、复用 | 主责附恢复动作、产物和原验收条件，指定验收人签认相应范围。首件通过只收首件，失败仅退受影响部分。实际验收人沿同一条验收说明注明已有案例 ID、实际已交知识管理员、或一次性问题略过。值得复用的案例异步查重、按文档 ID 读回；下一次复用后在原卡留检查结果。 | 执行接手、父 Run 结束、业务验收分别有据。知识整理按现有规则异步办理，业务可以按验收结果继续。 |

按现行分工，上述截面可在原卡回“r3 候选已交。现行生产读取范围待核，实际生成受影响。请现任协调员落实能提供生产部署引用的具名对口。引用到达后，由项目负责人复验受影响支路。”提出新前置条件时说明所依据的现行授权、验收条件或实际系统行为。已有授权覆盖、两种检查结果都指向同一动作时，直接续办。复查点到期要查原答复和在途，记录此次处置及恢复条件。

### 试点和自动提醒边界

由现有责任人决定到点后的动作，复用原卡、现有提醒与知识管理员。腾讯 `unblock` 对登记检查点向现任协调员提醒一次，项目负责人按原委托推进。已有具名接手、在途或待外部授权时沿原请求核收。若试点复现漏接或漏提醒，再针对失败入口评估自动化。

用隔离卡查三个结果：获准的独立支路能先交付、缺证到期能找到具名处置、同一检查点重放时新增派发为零。后续若补入有效原件，只恢复剩余动作，指定验收人签认对应范围。复盘可比较首次阻塞到首个可验证动作的耗时和重复派发次数。对真实阻塞耗时和解阻率的改善，还需要有可比条件的业务样本。

## 哪些问题值得自动处理

协调员最费时的环节是从多轮回件区分哪些事实仍有效，以及在重启后判断一次通知有没有送出。CLOU-40 中，原委托早已落盘；负责人确实接过取证任务，也核到当时执行令牌具备技术创建能力。现行生产扫描规则和业务放行仍须找有权方。单看 Run 终态或重复查权限都会得出错误的下一步。[原卡](http://10.207.56.3:3000/cloud-work/issues/01a1f9b0-ab24-7cf1-b748-8b5dc2c4e966)

采用一个可重放的核收流程。使用现有工作流、原 Issue 和可选的原 job。项目资料登记具名岗位、身份、职责范围、任职引用、有效时点；联系人、取证人及授权人分别填写。协调员通过自己在原线程发布的静默摘要确认当前观察。摘要引用证据和验收范围，产物、授权和验收结论仍由各自的原件提供。

处理顺序为已取消/暂停、状态不明或有在途、证据缺口、恢复、验收。数据缺页、跨项目来源和权限不足保留待核。存在多个获准路线且取舍影响交付时，用原件与 Decision MCP 比较并回填，确需历史经验才查获准的项目 bank。辅助服务不可用时按职责内决策权限及项目明定的审批要求办理。缺权限时直接落实有权人。

## 实现边界

1. **单一业务原件。** 在原 Issue 的固定线程上发布 `/note unblock.v1 <JSON>`，由登记的协调员身份维护，每个回合有单调修订号和检查点标识。独立支路沿同一 Issue 的不同原线程办理。同一动作沿用检查点或原交办请求 ID，新动作单独核验授权、归属和在途，保留旧接手回执供追溯。登记文件存受权的实例、项目、原卡、原线程、岗位及原件引用，供查到期、在途和历史处置。
2. **有限事件。** 仅观察已登记卡的补件、精确 Run 终态、绑定 job 版本增量及到期时间。来源数据只提出核收线索。以同卡、回合、检查点合并并发信号；无变化时静默。协调员摘要的原生发布时间和已核信箱版本是重读基线；SQLite 保存通知认领和回执。发出前落盘认领；网络结果未知只读对账，不能证明未发时保留待核，不换键补发。自动动作最多是一次对现任协调员的核收提醒。项目负责人收到的恢复授权和指定验收人的签认走原生流程。
3. **恢复与验收。** 区分技术能力、业务许可、生产隔离、实际执行和指定范围验收。只读首件校验读取普通源和副本，比对预期字节数、SHA-256 和源稳定性；既有文件、相同大小的错误内容、路径重解析及读途中变化应有不同结论。校验器只验证字节。业务验收由指定人对精确产物出具记录。
4. **可停用。** 登记按项目启用；隔离夹具和预览是交付入口。生产启用须明确实例、项目、协调员、原线程、原 job、读身份、目标通知权限和规则版本。停用时停止新通知，保留原件、水位及结果未知的请求，逐笔查原回执。协调员可继续使用现有 Skill 人工办理。

| 工作包 | 独立产物 | 主会话反例 |

| D 首件校验 | 只读回算源与目标及文件稳定性，返回可附原卡的脱敏结果 | 缺目标、同大小错摘要、既存一致、链接或并发改写 |

主会话组装日常入口及合成端到端演练，独立核对动作数、回执、运行和验收范围。实现、隔离验收、生产启用、CLOU-40 业务验收分别记账。原卡历史数据不作试写、重派或生产试点。

日常入口与项目停用步骤见[操作手册](unblock-operations.md)。开发归属为「Multica 运行时验证」的 [CLOU-49](http://10.207.56.3:3000/cloud-work/issues/01a1fd49-abe8-7d5f-ab4f-c39e4bdfed6f)，CLOU-50～53 分别承接表内四项。项目、Agent 与路径的示例数据均可替换为隔离夹具。

## 与现有 G8 定时巡查配合

G8 巡查逐页查信箱增量，独立查授权项目的到期、待接手和有变化的原卡。登记卡的 `summary`、`g8` 和 `tick` 预览可提供只读事实。按原 `job_id`、事件版本和摘要收结果，按原卡核具名接手、运行、验收与反馈。读回失败时保留待核，能查的一路照常查。需要本地处置的事项由原主责续办，协调员负责落实具名对口。[G8 巡查正文](g8-project-patrol-prompt.md)

已登记并明确授权的腾讯试点可走[原卡静默交接](unblock-operations.md#腾讯协调端与-g8-原卡交接)。该路由传递待核事项，协调端 `tick --apply` 是唯一提醒端，同卡同检查点沿原账本去重。受限网关通过 `get_job` 发现绑定信箱的版本变化。G8 按事件读取精确结果使用其已有获权客户端，两种身份分别核授权。

页水位表示该页事件已读回及回报记录已持久。交接结果未知时查原标识，相关事件保持待核。已持久交接后，可继续读新事件，具名业务接手仍以原卡证据为准。现有获准的单次读 ACK 例外按原标识独立维护。

| G8 巡查用例 | 预期回执、水位及动作 |
|---|---|
| 原水位 100，信箱空页，原卡到期 | 水位仍 100。原卡照常查，汇总原主责、已证卡点、缺项与复查点。 |
| 事件 101 完整、102 缺精确结果，另有登记卡到期 | 该页保留原水位。恢复后读原版本，101 的既有记录按原键去重。原卡的到期项继续核查。 |
| 已获准交办或登记试点交接，送达回包丢失 | 按同一卡及原请求 ID 对账。仍查不清时保留送达待核，重放不增加提醒或 Run。 |
| 首件回报已到，另一个支路仍缺许可 | 按原件收取首件与已有验收结论，同时如实报告另一支路。原主责沿原线程找有权人，授权或业务验收由对口人出具。 |

战略分析按需开展。例如多个项目确实竞争同一份有限资源，G8 可收集各项目的约束和交付影响，比较改序、分批或保留现状，给出推荐和可复核的依据。跨项目选择由具备相应权限的人确认后进入原卡。既有巡查继续报告事实，负责人照常交付已获准的工作。

复盘记录显示，方案选定后，历史听审证据已补到原卡，实际核对尚未落实到具名执行人。G8 在北京时间 20:32 补发原卡交办，请 Mike 落实现任负责人核对 P089 的原音登记和字幕片段版本。Mike 的 Run 留下了交办触发证据，执行人接手和生产迁移放行仍以各自原件确认。[CLOU-40 原卡](http://10.207.56.3:3000/cloud-work/issues/01a1f9b0-ab24-7cf1-b748-8b5dc2c4e966)

代码复核另发现，旧接手回执若只核签名，可能被带入同卡的新动作。这是隔离回归覆盖的复发风险。验收保留上一轮有效回执，再切换到 P089。系统保持执行待接手，直到收到匹配本次动作、目标和版本的新回执。仅有 Run 启动或发送结果未知时，继续沿原标识对账，复查保持同一提醒和 Run 计数。P089 回证只更新后期支路。C001 迁移支路须有独立的生产读取范围证据才可放行。
