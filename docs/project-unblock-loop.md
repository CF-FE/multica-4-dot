# Multica 原卡解阻：设计与验收

2026-11-21。本文交付工程设计。岗位、接单、回程和实际验收沿用 [workspace-coordination](../skills/workspace-coordination/SKILL.md#原卡解阻闭环)。架构选择及替代方案见 [ADR-006](decisions/006-project-unblock-loop.md)。

## 哪些问题值得自动处理

协调员最费时的环节是从多轮回件区分哪些事实仍有效，以及在重启后判断一次通知有没有送出。CLOU-40 中，原委托早已落盘；负责人确实接过取证任务，也核到当时执行令牌具备技术创建能力。现行生产扫描规则和业务放行仍须找有权方。单看 Run 终态或重复查权限都会得出错误的下一步。[原卡](http://10.207.56.3:3000/cloud-work/issues/01a1f9b0-ab24-7cf1-b748-8b5dc2c4e966)

采用一个可重放的核收流程。使用现有工作流、原 Issue 和可选的原 job。项目资料登记具名岗位、身份、职责范围、任职引用、有效时点；联系人、取证人及授权人分别填写。协调员通过自己在原线程发布的静默摘要确认当前观察。摘要引用证据和验收范围，产物、授权和验收结论仍由各自的原件提供。

## 岗位、动作和出口

| 观察 | 下一动作 | 确认完成的证据 |
|---|---|---|
| 下一动作已选，执行待接手 | G8 在原卡核清授权、同一动作的旧交办与在途后，由唯一派发者当轮交办一次。执行人未定时由现任协调员具名负责落实 | 读回原交办和复查点。具名执行人在原线程的回执须匹配本次检查点或原请求 ID 及目标和版本 |
| 只有入箱、指派或未知回执 | 发件人沿同一请求和原卡对账。确认未收到、无同一动作在途且已获准时，由唯一派发者提醒一次 | 接收方原生接手回执及可归因 Run 的各自原件 |
| 已接手，条件部分满足 | Mike 分项指定追证人和补证岗位；记录精确对象、证据、生效时间与检查点 | 已核项可复用；对象、身份或版本变化时重新核受影响项 |
| 条件到期仍缺，或查不到有权人 | 协调员沿原 job 交 G8，继续负责追踪直至 G8 核收；G8 确定下一责任人，或取得暂停、取消、调整范围的正式处置 | 原接收方的具名回证和下一检查点；已读 ACK 只证明读取 |
| 证据齐备、原授权仍有效 | 项目负责人核有无在途或已有产物，沿原步骤恢复一次 | 同一对象的真实执行与产物。写入结果未知时先只读找回 |
| 已执行、验收缺证或失败 | 核原产物，已有动作只补回执。确需修正时仅退回受影响项 | 指定验收人对明确范围作出结论；首件结论只覆盖首件 |

处理顺序为已取消/暂停、状态不明或有在途、证据缺口、恢复、验收。数据缺页、跨项目来源和权限不足保留待核。存在两个以上获准且可行的路线并影响交付时，使用原件、获准项目 bank 及 Decision MCP 比较并回填。缺权限时直接落实有权人。

负责人推进职责内的解阻动作，需要协同时交工作区协调员，协调员无法落实有权人或处置时交 G8（云端 Dot）兜底。每次移交沿原线程留痕，交出方跟到接手回执可读回。并行补证和执行动作具名交办并分别确认接手，缺业务授权的原动作继续作为受阻支路追证。整卡按真实进展推进，确无可行动作时由获授权人依据原件评估标记阻塞，并保留具名解阻责任人、缺项和复查点。巡查输出建议，状态依原工作流核回。

## 实现边界

1. **单一业务原件。** 在原 Issue 的固定线程上发布 `/note unblock.v1 <JSON>`，由登记的协调员身份维护，每个回合有单调修订号和检查点标识。独立支路沿同一 Issue 的不同原线程办理。同一动作沿用检查点或原交办请求 ID，新动作单独核验授权、归属和在途，保留旧接手回执供追溯。登记文件仅存受权的实例、项目、原卡、原线程、岗位及原件引用，G8 待办从这些原卡按需生成。
2. **有限事件。** 仅观察已登记卡的补件、精确 Run 终态、绑定 job 版本增量及到期时间。来源数据只提出核收线索。以同卡、回合、检查点合并并发信号；无变化时静默。协调员摘要的原生发布时间和已核信箱版本是重读基线；SQLite 保存通知认领和回执。发出前落盘认领；网络结果未知只读对账，不能证明未发时保留待核，不换键补发。自动动作最多是一次对现任协调员的核收提醒。项目负责人收到的恢复授权和指定验收人的签认走原生流程。
3. **恢复与验收。** 区分技术能力、业务许可、生产隔离、实际执行和指定范围验收。只读首件校验读取普通源和副本，比对预期字节数、SHA-256 和源稳定性；既有文件、相同大小的错误内容、路径重解析及读途中变化应有不同结论。校验器只验证字节。业务验收由指定人对精确产物出具记录。
4. **可停用。** 登记按项目启用；隔离夹具和预览是交付入口。生产启用须明确实例、项目、协调员、原线程、原 job、读身份、目标通知权限和规则版本。停用时停止新通知，保留原件、水位及结果未知的请求，逐笔查原回执。协调员可继续使用现有 Skill 人工办理。

## 并行交付与复核

| B 到件／到期去重 | 有限登记、持久认领、水位与精确回执恢复 | 并发、丢响应重启、信号乱序、到期与补件同时发生 |
| C 原生接入 | 读原卡、原线程及原 Run，核身份和归属；精确通知协调员并只读对账；绑定的信箱版本作为变更线索 | 错作者、相邻项目、截断、换任、同名通知、原生读取失败 |

## 与现有 G8 定时巡查配合

G8 定时任务拥有自己的授权项目范围、事件游标、内部回程与时段频率。其逐页查增量和独立查到期两路并行；登记卡的 `summary`、`g8` 和 `tick` 预览可提供只读事实。原卡侧获准发送提醒的 `tick --apply` 属于协调端。G8 巡查只发交接，同一原卡、同一回合只由一个获准执行端唤醒。已登记腾讯协调端的卡可显式授权 [原卡静默备注交接](unblock-operations.md#腾讯协调端与-g8-原卡交接)，腾讯端只读取原卡即可触发这一路提醒。受限网关通过 `get_job` 发现绑定信箱的版本变化；按事件读精确版本和摘要使用 G8 已有的获权客户端。两种身份的权限保持独立。[G8 巡查可转发正文](g8-project-patrol-prompt.md)

核对空事件页＋到期卡、读取一路失败＋另一路可查、同一事件重放、内部投递结果未知、已投递待接手、仅首件通过六种情形。页水位表示事件核查与持久交接的位置；原待办继续承担接手和验收跟踪。无可读回内部入口时保持交接未完成；不得把本地生成摘要或补报器记录当作 G8 接手。G8 定时任务加载新正文、真实内部回执及其游标恢复须在该 G8 环境另验。现有单次 ACK 例外按原标识独立维护。

| G8 提示词桌面推演输入 | 预期回执、水位及动作 |
|---|---|
| 原水位 100，空页，同卡检查点已到 | 水位仍 100；核查原卡，具名追证。本回合已有持久交接时复用。 |
| 事件 101 完整、102 缺精确结果；另一张登记卡到期 | 该页水位仍 100；独立到期卡照常核查。恢复后读原版本，101 的既有交接按原键去重。 |
| 101、102 均核实，102 需交接，投递响应丢失 | 先读原交接 ID，查不清则保留原水位与“交接未完成”。若原持久回执已核，水位可到 102，G8 实际接手仍待原生证据。 |
| G8 新回件与定时复查同时到，或首件核验通过 | 同一回合一次核收。分别记录接手、首件产物和验收范围；整卡关闭按原约定。 |

### 云端 Dot 下次更新

在云端 Dot 的自定义指令中合并以下增量，原有授权边界继续适用。

> 我是 G8，负责兜底推进已授权项目的解阻。方案确定后，当轮沿原 Issue 和原线程落实下一动作。授权明确、尚未交办且已核无同一动作在途时，由唯一获准派发者交办一次，记具名执行人、目标与版本、预期证据、稳定请求或检查点及复查点。执行人待定时由现任协调员具名落实，交出方跟进到接手回执可读回。交办、送达、Run 启动和执行接手分别核实。只有具名执行人对该动作、目标和版本的原生回执才确认接手。未知结果沿原标识对账。可独立推进的获准支路继续交办，缺授权的支路继续追证。凭原系统证据确认恢复，由指定验收人确认相应范围后收尾该支路。

更新原有两条云端巡查计划的正文，统一复制 [G8 定时任务 Prompt](g8-project-patrol-prompt.md)。工作时段每 15 分钟、休息时段每 30 分钟，沿用现有计划与时区。保留计划的授权范围、回程和当前已核游标。尚未确认完成的单次读 ACK 例外继续沿原授权、固定标识和校验条件办理。回退时恢复上次读回的自定义指令和两条计划正文，继续沿当前已核游标，按原交办 ID 对账。

在原云端会话确认工具实际可调用。Multica 先按实例、工作区、项目核 `get_coordinator`、`list_issues`、`get_issue`，再用 `list_issue_runs` 或 `get_run` 查运行证据。接手须能查原线程、回执作者和本次动作。可以用获准的原生原件或由当值协调员提供可复核的原件引用。Task Mailbox 从原游标读事件，并按 job、版本及摘要核原结果。任一路缺权限或原件不可见时，逐项标出待核和具名跟进人，其他可核事项继续查。写入入口或授权缺失时保留待接手，交现任协调员落实。已登记腾讯协调端的卡按获准的静默交接流程办理，提醒继续由该唯一发送端发出。

保存后在原云端 Dot 中逐项读回自定义指令及两条计划的完整正文、计划 ID、触发频率、时区和启用状态。用隔离原卡验证空信箱时仍查得到期和待接手，旧接手回执、Run 已启动以及送达未知分别维持待接手。随后在隔离卡获准交办一次，读回原请求、线程、具名接手回证及 Run，重放检查点后比较提醒和 Run 数。用两个线程分别验收独立后期与缺授权迁移。两条计划各观察一次真实触发，核对执行身份、原卡读回、回程与游标推进情况。此节是更新与验收步骤，实际结果须由云端回执确认。

## CLOU-40 复盘与隔离验收

复盘记录显示，方案选定后，历史听审证据已补到原卡，实际核对尚未落实到具名执行人。G8 在北京时间 20:32 补发原卡交办，请 Mike 落实现任负责人核对 P089 的原音登记和字幕片段版本。Mike 的 Run 留下了交办触发证据，执行人接手和生产迁移放行仍以各自原件确认。[CLOU-40 原卡](http://10.207.56.3:3000/cloud-work/issues/01a1f9b0-ab24-7cf1-b748-8b5dc2c4e966)

代码复核另发现，旧接手回执若只核签名，可能被带入同卡的新动作。这是隔离回归覆盖的复发风险。验收保留上一轮有效回执，再切换到 P089。系统保持执行待接手，直到收到匹配本次动作、目标和版本的新回执。仅有 Run 启动或发送结果未知时，继续沿原标识对账，复查保持同一提醒和 Run 计数。P089 回证只更新后期支路。C001 迁移支路须有独立的生产读取范围证据才可放行。
