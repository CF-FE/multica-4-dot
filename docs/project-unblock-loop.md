# Multica 原卡解阻：设计与验收

2026-11-21。本文交付工程设计。岗位、接单、回程和实际验收沿用 [workspace-coordination](../skills/workspace-coordination/SKILL.md#原卡解阻闭环)。架构选择及替代方案见 [ADR-006](decisions/006-project-unblock-loop.md)。

## 哪些问题值得自动处理

协调员最费时的环节是从多轮回件区分哪些事实仍有效，以及在重启后判断一次通知有没有送出。CLOU-40 中，原委托早已落盘；负责人确实接过取证任务，也核到当时执行令牌具备技术创建能力。现行生产扫描规则和业务放行仍须找有权方。单看 Run 终态或重复查权限都会得出错误的下一步。[原卡](http://10.207.56.3:3000/cloud-work/issues/01a1f9b0-ab24-7cf1-b748-8b5dc2c4e966)

采用一个可重放的核收流程。使用现有工作流、原 Issue 和可选的原 job。项目资料登记具名岗位、身份、职责范围、任职引用、有效时点；联系人、取证人及授权人分别填写。协调员通过自己在原线程发布的静默摘要确认当前观察。摘要引用证据和验收范围，产物、授权和验收结论仍由各自的原件提供。

## 岗位、动作和出口

| 观察 | 下一动作 | 确认完成的证据 |
|---|---|---|
| 只有入箱、指派或未知回执 | 发件人查同一请求和原卡；确无在途且原授权允许时由唯一派发者唤醒一次 | 接收方原生接手回执；另查可归因 Run 的开始时间 |
| 已接手，条件部分满足 | Mike 分项指定追证人和补证岗位；记录精确对象、证据、生效时间与检查点 | 已核项可复用；对象、身份或版本变化时重新核受影响项 |
| 条件到期仍缺，或查不到有权人 | 协调员沿原 job 交 G8，继续负责追踪直至 G8 核收；G8 确定下一责任人，或取得暂停、取消、调整范围的正式处置 | 原接收方的具名回证和下一检查点；已读 ACK 只证明读取 |
| 证据齐备、原授权仍有效 | 项目负责人核有无在途或已有产物，沿原步骤恢复一次 | 同一对象的真实执行与产物。写入结果未知时先只读找回 |
| 已执行、验收缺证或失败 | 核原产物，已有动作只补回执。确需修正时仅退回受影响项 | 指定验收人对明确范围作出结论；首件结论只覆盖首件 |

处理顺序为已取消/暂停、状态不明或有在途、证据缺口、恢复、验收。数据缺页、跨项目来源和权限不足保留待核。存在两个以上获准且可行的路线并影响交付时，使用原件、获准项目 bank 及 Decision MCP 比较并回填。缺权限时直接落实有权人。

## 实现边界

1. **单一业务原件。** 在原 Issue 的固定线程上发布 `/note unblock.v1 <JSON>`，由登记的协调员身份维护，每个回合有单调修订号和检查点标识。检查点代表同一轮待核事项；新的授权或恢复命令须单独核验。登记文件仅存受权的实例、项目、原卡、原线程、岗位及原件引用；G8 待办从这些原卡按需生成。变更范围后重新核归属和在途。
2. **有限事件。** 仅观察已登记卡的补件、精确 Run 终态、绑定 job 版本增量及到期时间。来源数据只提出核收线索。以同卡、回合、检查点合并并发信号；无变化时静默。协调员摘要的原生发布时间和已核信箱版本是重读基线；SQLite 保存通知认领和回执。发出前落盘认领；网络结果未知只读对账，不能证明未发时保留待核，不换键补发。自动动作最多是一次对现任协调员的核收提醒。项目负责人收到的恢复授权和指定验收人的签认走原生流程。
3. **恢复与验收。** 区分技术能力、业务许可、生产隔离、实际执行和指定范围验收。只读首件校验读取普通源和副本，比对预期字节数、SHA-256 和源稳定性；既有文件、相同大小的错误内容、路径重解析及读途中变化应有不同结论。校验器只验证字节。业务验收由指定人对精确产物出具记录。
4. **可停用。** 登记按项目启用；隔离夹具和预览是交付入口。生产启用须明确实例、项目、协调员、原线程、原 job、读身份、目标通知权限和规则版本。停用时停止新通知，保留原件、水位及结果未知的请求，逐笔查原回执。协调员可继续使用现有 Skill 人工办理。

## 并行交付与复核

| 工作包 | 独立产物 | 主会话反例 |
|---|---|---|
| A 原卡摘要和责任判断 | 校验登记范围和核收摘要、按项目列 G8 在途及历史处理结果 | 技术允许但缺放行、接手缺证、G8 已签收、已暂停、首件与整卡 |
| B 到件／到期去重 | 有限登记、持久认领、水位与精确回执恢复 | 并发、丢响应重启、信号乱序、到期与补件同时发生 |
| C 原生接入 | 读原卡、原线程及原 Run，核身份和归属；精确通知协调员并只读对账；绑定的信箱版本作为变更线索 | 错作者、相邻项目、截断、换任、同名通知、原生读取失败 |
| D 首件校验 | 只读回算源与目标及文件稳定性，返回可附原卡的脱敏结果 | 缺目标、同大小错摘要、既存一致、链接或并发改写 |

主会话组装日常入口及合成端到端演练，独立核对动作数、回执、运行和验收范围。实现、隔离验收、生产启用、CLOU-40 业务验收分别记账。原卡历史数据不作试写、重派或生产试点。

日常入口与项目停用步骤见[操作手册](unblock-operations.md)。开发归属为「Multica 运行时验证」的 [CLOU-49](http://10.207.56.3:3000/cloud-work/issues/01a1fd49-abe8-7d5f-ab4f-c39e4bdfed6f)，CLOU-50～53 分别承接表内四项。项目、Agent 与路径的示例数据均可替换为隔离夹具。

## 与现有 G8 定时巡查配合

G8 定时任务拥有自己的授权项目范围、事件游标、内部回程与时段频率。其逐页查增量和独立查到期两路并行；登记卡的 `summary`、`g8` 和 `tick` 预览可提供只读事实。原卡侧获准发送提醒的 `tick --apply` 属于协调端。G8 巡查只发内部交接，同一原卡、同一回合只由一个获准执行端唤醒。受限网关通过 `get_job` 发现版本变化；按事件读精确版本和摘要使用 G8 已有的获权客户端。两种身份的权限保持独立。[G8 巡查可转发正文](g8-project-patrol-prompt.md)

核对空事件页＋到期卡、读取一路失败＋另一路可查、同一事件重放、内部投递结果未知、已投递待接手、仅首件通过六种情形。页水位表示事件核查与持久交接的位置；原待办继续承担接手和验收跟踪。无可读回内部入口时保持交接未完成；不得把本地生成摘要或补报器记录当作 G8 接手。G8 定时任务加载新正文、真实内部回执及其游标恢复须在该 G8 环境另验。现有单次 ACK 例外按原标识独立维护。

| G8 提示词桌面推演输入 | 预期回执、水位及动作 |
|---|---|
| 原水位 100，空页，同卡检查点已到 | 水位仍 100；核查原卡，具名追证。本回合已有持久交接时复用。 |
| 事件 101 完整、102 缺精确结果；另一张登记卡到期 | 该页水位仍 100；独立到期卡照常核查。恢复后读原版本，101 的既有交接按原键去重。 |
| 101、102 均核实，102 需交接，投递响应丢失 | 先读原交接 ID，查不清则保留原水位与“交接未完成”。若原持久回执已核，水位可到 102，G8 实际接手仍待原生证据。 |
| G8 新回件与定时复查同时到，或首件核验通过 | 同一回合一次核收。分别记录接手、首件产物和验收范围；整卡关闭按原约定。 |
