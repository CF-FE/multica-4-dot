# ADR-006　沿原 Issue 解阻与定向核收

**状态**　Proposed · 2026-11-21 创建，2026-11-25 修订职责条款。公子已明确云端 Dot 的职责和 Multica 内的交付分工。原提案中复用 Multica 与 Task Mailbox 的方向已获确认，生产启用和业务验收按各自原件核实。

## 背景

原卡能记录接单、Run、检查点及回程，但同一事项的证据分散在多个回件中。一次到期与一份迟到的补件可能让两边同时唤醒；已获技术写权限也容易被读成业务许可。CLOU-40 的首件取证和 CLOU-23 的额外复审分别暴露了这两类问题。[实施依据](../project-unblock-loop.md) · [工作流原件](../workflow-reporting.md)

## 决策与后果

11 月 21 日草案把解阻兜底交给 G8。CLOU-63 中，已有回件无法证实 C001 首句是否提交。即使 G8 读回这份回件，仍须有人查原提交记录或找到登记对口。将核账留在项目侧，能少一次无助于取证的交接。11 月 25 日按公子明确的职责修订如下。[CLOU-63 原卡](http://10.207.56.3:3000/cloud-work/issues/01a20c81-4de2-7336-b663-eeea80f3ab47)

- **项目内交付。** 项目负责人沿原 Issue 查因、补缺、回证。对口不清时，工作区协调员负责找到具名接收人并读回其对当前动作的签收。超出授权的具体事项由有权人决定，指定验收人按实际范围签认。
- **跨端交办与回程。** G8 单向下发已授权目标，用原请求核对是否送达，查询进度、收取结果与反馈。若同一请示已有具名跟进人，G8 沿原单收回进展。原 Issue 保存协调员核收的版本化摘要，回件分别引用实际接手、Run、产物和验收原件。
- **全局提案。** 多个项目反复遇到同类问题、共用依赖影响长期交付，或公子明确委托时，G8 比较维持现状与可行替代，给出推荐、代价和能改变结论的证据。重要取舍可受托起草 ADR，写清最小试点、实施与验收角色、成功条件和回退。由有权人决定是否采纳，实施范围获准后才交办。G8 回收试点反馈，建议推广、调整或停止。待议期间，项目负责人继续已授权工作。[职责与提案规范](../../skills/workspace-coordination/SKILL.md#g8-如何提出值得采纳的建议)

自动化只消费显式登记的来源，将有增量或已到期的检查点合并为一次核收提示。信箱按原 `job_id` 保存委托和版本化回件。提醒由登记的唯一发送端沿原检查点发给现任协调员，响应未知时沿原请求只读对账。v1 中的 `g8_acceptance` 用于追溯跨端收件。若旧摘要将 G8 列为后续业务主责，协调员在原线程追加修订，引用现任责任人的接手原件；尚无签收则记待接手并具名跟进。保留旧回执，读确认、执行接手和业务验收分别取证。[v1 摘要协议](../unblock-record-format.md) · [ADR-003 派发](003-command-delivery.md) · [ADR-004 回程](004-reporting-and-recovery.md)

G8 现有定时任务负责授权范围内的只读巡查及内部交接；项目侧单次提醒另核授权。两侧共用原件和检查点，保留各自的水位：巡查页需核清原版本、读回必要内部交接才推进；项目侧按协调员签认摘要及通知认领恢复。已读、已投递、已接手与业务验收各有独立依据。沿用现有巡查频率，单次读 ACK 的历史例外保持原限定。[两条路径如何配合](../project-unblock-loop.md#与现有-g8-定时巡查配合)

## 比较和撤销

仅靠 Skill 上手成本最低，跨回合恢复依赖人工整理；适合作为回退。全板固定轮询能找出遗漏，但每轮无变化仍可能启动 Agent。新建项目工作流能统一状态和处理人，却把多个独立证据压成一个状态，共用工作流时还影响其他项目。原卡摘要加窄范围的通知保留现场，代价是维护登记、核收习惯，以及诚实呈现投递不确定性。

指定项目停用时停止新提醒并对账在途，保留原回执与人工路径。仅当受控试点证明漏接仍然存在、且现有原生入口无法弥补，才另审全局监听或专用工作流。[试点及验收](../project-unblock-loop.md#并行交付与复核)
