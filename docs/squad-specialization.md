# 小队专精建设指引

建队者先填一句：**遇到〔实际问题〕，本队交付〔接手方能使用的结果〕，由〔验收人〕凭〔证据〕确认〔通过范围〕。** 如果已有小队能交付，就沿原卡交给它；确需新队时，写清新队独有的交付、与已有角色的分工，以及超出授权时由谁决定。[工作区角色库](role-library.md) · [小队派工与独立复审](../skills/workspace-coordination/SKILL.md#小队派工和独立复审)

## 从实际交付选专精

| 从原卡看到了什么 | 适合留下什么 | 两队的判断 |
|---|---|---|
| 一次性岗位或派工演练 | 原卡回执；待以后真实任务需要时再提取 | CLOU-79 中成员实现、队长复跑同一函数，证实了交接。没有业务调用需求时，保留这个证据就够了。 |
| 多处调用需要相同的输入、输出和失败处理 | 先找成熟实现，再决定是否提取组件。代码、回归和最短示例随所属项目维护 | CLOU-94 用两份真实 WAV 验证了核验组件。文件身份可复算，听感和放行留给项目按原约定判断。[开发索引](development-reuse.md) |
| 不同对象可以沿用同一判断步骤，处置却随项目变化 | 登记方法：要回答的问题、最短检查、何时适用、何时停止 | CLOU-14／18 用原操作和文档核收已完成的留存；复用的是“已完成就跳过”这一步。质量小队在 CLOU-94 复验修正点及相邻叙事，在 CLOU-68、75 按直接证据限定审核结论。[开发索引](development-reuse.md) · [质量索引](quality-review-methods.md) |

没有历史首例时，可以先写预期能力、可验收的输出和已有依据，在下一个自然到来的对口任务查验。一次真实失败也值得留下，尤其是它能说明某种方法在什么条件下失效。

## 填好就能用的小队指令

> 本队承接〔问题和授权范围〕，依据〔输入或候选版本〕交付〔结果及证据〕，由〔指定验收人〕按〔标准〕核收。队长沿原 Issue 接手并汇总，简单事项直接办；需要协作时按缺口交给〔适配成员〕，约清交付和回程。〔独立性要求、超出权限的对口人及停止条件，按本队实际填写。〕新项目接单先按问题查〔本队索引〕。实际采用后，队长随原卡交付或审核结论，将新增适用边界、实测结果和证据补回索引原条目及对应 bank 原文档。未采用就继续原任务，不专门找案例。

团队配置允许怎样执行、谁能批准、谁能独立签认，要按目标工作区和业务项目核实。开发队交付可运行候选并说明验证范围；质量队由未参与该版制作的人独立核验。两队共用原卡交接方式，各自承担原约定中的职责。

## 建完怎样验，之后谁维护

1. **配置已生效。** 读回小队 ID、现任队长、成员、完整指令和派工方式；在 Multica 用 `multica squad briefs <小队ID>` 确认队长和成员的简报都包含专精。此时可以登记“已配置”。
2. **首单验证能力。** 在下一笔真实项目原卡上，核对实际执行者、候选或产物、验收证据及范围。开发交付用真实输入跑通；质量审查指出哪项证据支持哪条结论。部分通过、失效或尚未覆盖的分支分别记录。另一个项目实际采用后，才补该项目的验证范围。
3. **维护随原卡完成。** 队长在原卡写下“用了什么／适用条件／结果或失效点／证据”。业务仓库存原件；小队索引按问题链接唯一入口；获准的 bank 保存选用理由和经验。按主题、来源、文档 ID 查重，已覆盖就引用，有增量才更新并按原 ID 读回。项目归属、写权限与业务验收沿原授权办理。

**索引条目模板**　〔什么问题值得查〕｜〔代码、方法或最短示例入口〕｜〔适用与失效条件〕｜〔实测项目、结果和原卡证据〕。现任队长维护入口，换任后沿用原条目和文档 ID。
