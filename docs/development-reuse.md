## 提交后断线，判断能否续办

CLOU-94 按来源位、原请求及逐件回执识别已完成、确认未提交、提交未知、实件不符。已完成的复用，只补确认未提交的，未知沿原请求核账。首件阶段可以暂缓两路；余量流程可继续独立的已确认缺项。这项目前登记为恢复方法。另一项目采用前先核其请求身份、逐件完成证据和独立执行条件；条件一致再提取共用代码。[中断夹具与恢复结果](http://10.207.56.3:3000/cloud-work/issues/01a21fcf-58c6-7b97-8361-4e8b30f062a9#comment-01a22012-3a70-70d5-8fc4-f4439e65225c)

CLOU-94 的受监督余量批次即使 Job 退出 0，也须逐来源位核对提交、返回、`wave.json` 和 WAV 实测摘要；单件不符只停该位，缺 Job 终态则停原次选中的来源位，只续办按原回执确认未提交的缺项。

### 第二个项目实证：跨会话核收已提交的 Hindsight 留存

「Multica 运行时验证」的 CLOU-18 提交一笔真实留存，CLOU-14 的 win-work Kimi 软件实现工程师随后沿原操作核收，跳过重复写入。两张卡属于同一项目，计一个场景；这是现任成员在小队成立前的交付。2026-11-28 按 CLOU-94 的方法独立做了一次只读对账：

1. 从原回执取操作号 `a1c9e026-71dd-4699-a682-83c5247606ac`，在 `multica-4-dot` 调用 `get_operation`。状态为 `completed`，操作指向原文档 `multica-hindsight-verified-20261120-wk`。
2. 用 `get_document` 读同一 bank 和文档 ID。将 `original_text` 原样编码为 UTF-8，实测 812 字节，SHA-256 为 `5d2e5fbfa9c0f8a9f27204e243bcd4a0cd69a5ac3309314ed9cf8cda748c8185`，与原卡登记一致。该项可直接核收，本轮对该原件写入 0 次。
3. 若状态、目标 ID 或内容对不上，就沿原操作查差异。本例验证“已完成分支”；真实网络断线、未知提交后的重投和并行补缺均未在该项目复演。WAV 组件仍只有凡人项目的实物验证。

## 何时补条目

同类任务出现时先更新已有条目。新条目写清解决的问题、代码或方法的唯一入口、最短示例、限制、真实验证项目。业务处置不同就分别记录；跨项目真实调用后才登记采用。通用经验存 multica-4-dot bank，先按问题、来源及现有文档 ID 查重，已有就补实质增量。
