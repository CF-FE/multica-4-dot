# 原请求与回程对账

## 先核原请求

| 实际观察 | 处理 |
| --- | --- |
| 已受理，原生对象待核 | 保留已受理和查询时间，按原认证主体及同一 `request_id` 继续查请求。 |
| 断线、超时，或服务无法确认写入 | 先通过已发现的只读能力查同一请求、实际 Issue 与 Run，记录是否可完整核对。保留不确定状态，交原派发者处理。获得该动作的明确恢复指引时才按原 ID 和原输入恢复。 |
| 同一 ID 与原指令范围、目标或内容冲突 | 停止，该 ID 仍指原指令。核对原件与当前授权，新意图按独立操作办理。 |
| 原 Issue 关联已核实 | 记录实际 Issue UUID、项目和承接人，按已授权范围核 Run。尚无 Run 证据时保留待排队或待核状态，按原生回执区分。 |
| 已授权的返工、重跑或其他独立后续动作 | 为该新动作保存独立请求 ID，保留原业务关联、原 Issue 与历次 Run。 |

重试沿原 ID 和原输入。未知请求与空列表都不足以证明零副作用，避免换 ID、换入口或另开一张卡。Decision Service 的 `request_id` 只用于其原决策读回，Multica 交办请求另有自己的记录。

## 追到原件

1. **Multica。** 按实例 / 工作区 / 项目 / Issue / Run 核原生关系、状态、发生时间、核读时间及受权产物引用。运行机离线时报告原生的排队或阻塞证据。产物没查到记为交付待核。
2. **Task Mailbox。** 约定信箱回程时核原 `job_id`、结果 `event_id`、版本与 `result_hash`。发起回报的一方沿原事件确认持久化。原收件人读回对应版本、核正文与摘要后按授权显式签收，并核匹配的读确认。读确认会写入信箱。仅协调员自报或独立 Run 观测时，注明来源和核取范围。普通 Multica 内部任务按原项目回报。
3. **业务验收。** 由指定验收人在原项目记录实际 Run、产物版本和结论。回执引用到同一原件。缺少来源或证据时说明未知项及谁能核实。
